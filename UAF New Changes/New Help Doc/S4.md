## Why Stage 2 needed the same realignment treatment as Stage 1

Stage 2's backend (migration 234, still live pre-238) mirrors Stage 1's *original*
shape from migration 233 — the shape that turned out not to match the real business
flow and had to be corrected by 237. Validating a Stage 2 business-flow spreadsheet
against 234 (same exercise as Sprint 3 did for Stage 1) surfaced the expected mirror
of every Stage 1 gap, plus some Stage-2-specific differences:

| Gap | 234 as merged | Agreed flow |
|---|---|---|
| No plan round | Stage 2 began at report upload | Plan uploaded, client accepts/rejects, **then** audit happens |
| No audit date | — | CRM/Auditor sets a manual Stage 2 Audit Date |
| Report + NCR split | Two statuses, two date stamps | One status, no date |
| RCA review gate too narrow | Auditor only | Auditor or CRM Office |
| Evidences review gate too narrow | Auditor only | Auditor or CRM Office |
| **Tail structure** | close→final-signoff (2 more RPCs after findings) | **Confirmed: no equivalent — findings goes straight to CDC upload** |
| No CDC step | — | CRM or Tech uploads CDC report; upload **is** the approval |
| No registration step | — | Manual registration date, explicitly sets `status__a` |

**The tail is a genuine divergence from Stage 1, not a mirror of it** — confirmed with
the stakeholder rather than assumed. Stage 1 kept its two-RPC tail
(`close_stage1_audit` → `accept_stage1_tech_review`) because inverting or collapsing
it was explicitly rejected in Sprint 3. Stage 2's spec has no equivalent rows at all;
`close_stage2_audit` and `accept_stage2_tech_review` are **retired** — left defined in
the database (not dropped) but never called by the frontend and never reached by any
upload or RPC.

## Two Stage 1 follow-up corrections (also in 238)

These came out of re-reviewing Stage 1 while validating Stage 2's spec, and are
**Part A** of migration 238:

1. **`stage1_audit_date__a`: DATE → TEXT.** Built as DATE in 237; confirmed it should
   be free text (matching Stage 2's equivalent field, which the stakeholder
   explicitly specified as text). `ALTER COLUMN ... TYPE TEXT`, plus the
   `tenant.fields` row's `type` updated from `date` to `text`.
2. **`stage1_ncr_rca` upload no longer stamps `stage1_ncr_rca_uploaded_date__a`.**
   Confirmed: this date isn't wanted, matching how Stage 2's spec never captures a
   date for the equivalent client-upload step. The **column is not dropped** (kept for
   any historical data) — stakeholder's explicit instruction: stop writing to it, keep
   it, and it "shall never be under consideration in the flow" going forward. Same
   treatment applied to `stage2_ncr_rca_uploaded_date__a` — that one is built retired
   from day one rather than added then removed.

**Do not read either orphaned column anywhere** — not in RPCs, not in
`StageAuditActionPanel`, not in `ClientWorkflowBar`'s `dateKey` mapping. Both stages'
"RCA Done" stage entries have `dateKey: ''`.

## Status flow (full pipeline after 238, single bar)

```
... Stage1_Complete ("Ready for Stage 2")
  → Stage2_Plan_Sent            (CRM/Auditor uploads Stage_two_audit_plan — auto)
  → Stage2_Plan_Accepted        (client accepts plan)
  → Stage2_Report_Sent          (CRM/Auditor uploads report and/or NCR — auto, merged, no date)
  → Stage2_NCR_RCA_Uploaded     (client uploads NCR + RCA — auto, no date)
  → Stage2_Auditor_Accepted     (auditor/CRM accepts RCA)
  → Stage2_Evidences_Uploaded   (client uploads evidences — auto, date kept)
  → Stage2_Evidences_Accepted   (auditor/CRM accepts evidences — shown as "Stage 2 NCR Closed")
  → Stage2_Tech_Findings_Given  (tech submits findings, or accepts w/o — shown as "Stage 2 Tech Review Passed")
  → CDC_Approved                (CRM or Tech uploads CDC report — auto, upload IS approval)
  → Client_Registered           (CRM/Auditor records registration date — explicit RPC)
```

**Reject step-backs:** client rejects plan → stays `Stage2_Plan_Sent` + client remarks
(now correctly cleared on re-upload — see "Bug caught and fixed" below); auditor/CRM
rejects RCA → `Stage2_Report_Sent` + auditor remarks; auditor/CRM rejects evidences →
`Stage2_Auditor_Accepted` (client only redoes evidences, not the whole RCA round) +
remarks. No reject path for tech findings, CDC upload, or registration — matches
Stage 1's precedent (one-way past that point) and the spec (no reject rows for those
steps).

**Retired statuses:** `Stage2_Report_Uploaded`, `Stage2_NCR_Uploaded` (merged, deactivated
in `tenant.picklist_values`, live records migrated forward). `Stage2_Closed` is also
deactivated (tail restructured) — **`Stage2_Complete` is deliberately left active**,
since unlike the merged pair it has no 1:1 replacement target; any record already
sitting on `Stage2_Closed`/`Stage2_Complete` from old testing is left as-is rather than
force-migrated into an unfamiliar new terminal state.

## Migration 238 — [`238_stage2_workflow_and_stage1_followup.sql`](../../supabase/migrations/238_stage2_workflow_and_stage1_followup.sql)

| Part | Contents |
|---|---|
| A | Stage 1 follow-up: `stage1_audit_date__a` DATE→TEXT; drop the `stage1_ncr_rca` upload date stamp (moved into Part C) |
| B1–B4 | Stage 2 new columns, field registration (`stage2_audit_date` text, `cdc_report` file — **registration date is deliberately NOT a registered field**, see below), picklist registration, live-record migration |
| B5 | **New RPC** `review_stage2_plan` — mirrors `review_stage1_plan` exactly |
| B6–B7 | **Redefined** `review_stage2_ncr_rca` / `review_stage2_evidences` — gates widened to CRM, reject targets repointed |
| B8 | **New RPC** `set_stage2_registration_date(p_record_id, p_date)` — sets both the date and `status__a = 'Client_Registered'` in one call |
| C | **Redefined** `finalize_file_upload` — supersedes 237. Adds `Stage_two_audit_plan`, merged `stage2_report`/`stage2_ncr`, `stage2_ncr_rca` (no date), unchanged `stage2_evidences`, new `cdc_report` blocks. **Must run after 237** if migrations are ever replayed. |
| D | Grants |

**`registration_date` is panel-only, not a generic field** — per the stakeholder's
"explicit status write via small RPC" decision, it's captured through
`StageAuditActionPanel`'s own `<input type="date">` + Confirm button, not the generic
edit form, so the RPC (and its `status__a` write) fires on save. This is the only
Stage 1/2 date that works this way; every other manual date (`stage1_audit_date`,
`stage2_audit_date`) is a plain registered field with no status implication, matching
the spec explicitly leaving those rows' "Next step"/"Stage Status" columns blank.

**CDC gate** — new `_is_crm_or_tech` boolean inside `finalize_file_upload` (admin OR
`%crm%` OR `%tech%`), alongside the existing `_is_crm`/`_is_crm_or_auditor`. Upload
auto-advances directly to `CDC_Approved` — no separate accept RPC, matching the spec
("just uploads the CDC report... CDC approved").

**`registration_date` RPC gate** — set to CRM-or-Auditor. The spec's "Manual entry" row
didn't name a role; this is an assumption, not a confirmed decision — revisit if the
wrong role ends up needing it.

### Bug caught and fixed before this shipped

While building the Stage 2 plan-review panel (which is structurally identical to
Stage 1's), re-examining Stage 1's plan logic surfaced a real bug that was already
live in 237: **`stage1_plan_client_remarks__a` is only cleared on RPC accept, never on
re-upload.** Since the "revise plan" prompt (CRM/Auditor) and the "review plan" panel
(client) are both gated on the *same* status value (`Stage_one_plan_Sent`/`Stage2_Plan_Sent`
— unlike every other checkpoint pair, which use distinct statuses), a client who
rejects the plan would see their own review panel reappear — with stale remarks —
the moment CRM/Auditor re-uploads, before the panel logic could tell "fresh revision"
apart from "still the rejected one." Fixed in 238's `finalize_file_upload`: both the
`stage_one_audit_plan` and `Stage_two_audit_plan` upload blocks now clear their
respective remarks column on **every** upload, not just on RPC accept. This is a
correction to already-applied 237 behavior, delivered via 238 since 237 can't be
edited retroactively.

## Frontend

### [`StageAuditActionPanel.tsx`](../../app/commonfiles/core/components/custom/External_Client/StageAuditActionPanel.tsx) — Stage 2 checkpoints

Extended in place, per the sprint plan ("extend the Sprint 3 panel, not a separate
component"). All Stage 1 logic is untouched except the bug fix above (which lives in
the migration, not the component).

| Checkpoint | Shown to | Gate (`status__a`) | RPC |
|---|---|---|---|
| Upload / revise Stage 2 plan | CRM / Auditor | `Stage1_Complete`, or `Stage2_Plan_Sent` + client remarks | — (generic field) |
| Review Stage 2 plan | Linked client | `Stage2_Plan_Sent` + plan uploaded | `review_stage2_plan` |
| Conduct Stage 2 audit | CRM / Auditor | `Stage2_Plan_Accepted` | — (set date + upload via fields) |
| Upload Stage 2 NCR + RCA | Linked client | `Stage2_Report_Sent` | — (generic field) |
| Review Stage 2 NCR + RCA | Auditor or CRM | `Stage2_NCR_RCA_Uploaded` | `review_stage2_ncr_rca` |
| Upload Evidences | Linked client | `Stage2_Auditor_Accepted` | — (generic field) |
| Review Evidences | Auditor or CRM | `Stage2_Evidences_Uploaded` | `review_stage2_evidences` |
| Tech Review (findings or direct accept) | Tech Reviewer | `Stage2_Evidences_Accepted` | `submit_stage2_tech_findings` (notes optional, same trick as Stage 1) |
| Upload CDC Report | CRM or Tech Reviewer | `Stage2_Tech_Findings_Given` | — (generic field, upload is the approval) |
| Record Client Registration | CRM / Auditor | `CDC_Approved` | `set_stage2_registration_date` |

Entry into Stage 2 is gated on `status === 'Stage1_Complete'` for the plan-upload
prompt — an exact, unambiguous single value (unlike Stage 1's report/NCR prompts,
which had to use file-presence checks because the old 7-stage pipeline had no single
defined "ready for Stage 1" status).

**Remarks surfacing** (mirrors Stage 1's pattern exactly): `stage2_plan_client_remarks__a`
→ CRM/Auditor on the revise-plan prompt; `stage2_rejection_notes__a` → client on the
RCA upload prompt; `stage2_evidences_rejection_notes__a` → client on the evidences
upload prompt (new — Stage 1 has no evidences round). Admin fallback box now covers
all six Stage 1 + Stage 2 remarks columns.

**`stage2_tech_final_rejection_notes__a`** (from 234) has **no surfacing anywhere** —
it belongs to `accept_stage2_tech_review`, which is retired. The column is dead,
matching the two orphaned upload-date columns in spirit, though it wasn't explicitly
called out by the stakeholder the way those were.

### [`ClientWorkflowBar.tsx`](../../app/commonfiles/core/components/custom/External_Client/ClientWorkflowBar.tsx) — 10 more stages, same bar

`STAGES` grew from 12 to 22 entries — still one array, one bar, per the "I never
wanted 2 status bars" decision from Sprint 3. The 7-wide sliding window and `+N more`
expand mechanics are unchanged; the only code change was making the expanded view's
min-width scale with `STAGES.length` (`${total * 75}px`) instead of a hardcoded pixel
value, so it stays correct as more stages get added.

`stage1_audit_date__a`/`stage2_audit_date__a` (TEXT) are **not** in `STAGES` at all —
confirmed in Sprint 3 and still true here: the spec leaves those rows' status/next-step
columns blank, so they're plain fields on the layout, never bar dots.

No `RecordDetailView.tsx` changes were needed — Sprint 3's mount point already passes
`recordData` through unchanged; both components just read more keys off the same
object now.
