# External Client — Audit Workflow Backend (S0 · S1 · S2)

This document covers the backend implemented across three sprints on the External
Client object (`tenant.external_clients__a`):

- **S0** — hard-lock the `quotation` upload to CRM Office / admin.
- **S1** — the full Stage 1 certification-audit lifecycle (schema + RPCs).
- **S2** — the Stage 2 lifecycle, mirroring Stage 1 plus a client-evidences round.

> **⚠️ Superseded for Stage 1/2 — read S3.md and S4.md first.** Migrations 237 and
> 238 realigned this document's S1 and S2 sections to match the actual business flow
> (plan-round checkpoints, merged report/NCR steps, widened review gates, a
> restructured Stage 2 tail). Where they disagree with what's below, **S3.md /
> S4.md are current**. This document's **S0 section (quotation lock) is still
> accurate and untouched** by either realignment. Treat the S1/S2 sections below as
> historical background on how the workflow got to where S3/S4 leave it, not as the
> current design.

Everything here is **backend only** (DB migrations: columns, `tenant.fields`
registrations, RPCs, and `finalize_file_upload` auto-advance logic). The frontend
action panels and workflow stepper are a separate follow-up — see
**external-client-audit-workflow-sprint-plan.md** (Sprints 3–4) and the
**"Frontend not built yet"** note at the bottom.

Related docs: **file-upload-field.md**, **new-client-form.md**, **permission-sets.md**,

## Roles

Role gating uses the same convention as the pre-existing CRM flow — match on the
**custom role name** (case-insensitive substring), never a hardcoded role ID. Admin
(`system.users.role = 'admin'`) bypasses every gate.

| Role | Matched by | Acts on |
|---|---|---|
| CRM Office | `lower(role name) LIKE '%crm%'` | Quotation upload; Stage 1/2 report + NCR upload |
| Auditor | `lower(role name) LIKE '%auditor%'` | Stage 1/2 report + NCR upload; accept NCR+RCA; accept evidences; close audit |
| Tech Reviewer | `lower(role name) LIKE '%tech%'` | Submit findings; final sign-off |
| Linked client | `external_clients__a.client_user_id__a = auth.uid()` | Upload NCR root-cause (RCA); upload Stage 2 evidences |
| admin | `system.users.role = 'admin'` | Everything (bypass) |

> **Prerequisite:** the "Auditor" and "Tech Reviewer" roles must exist in
> `tenant.roles` with names containing `auditor` / `tech`. Until they do, the Auditor /
> Tech-Reviewer RPCs deny every non-admin caller. Names like "Auditor" and
> "Tech Reviewer" satisfy the `LIKE` patterns as-is.

## S0 — Quotation Upload Lock

**Problem it fixes:** previously any user with field-edit rights could upload the
`quotation` file — only the resulting `status__a` auto-advance was CRM-gated (inside
`finalize_file_upload`), not the upload itself.

**Fix:** a role gate inside `start_file_upload` (`016_file_upload_rpc_functions.sql`,
redefined in `232`), placed right after the object/field is resolved and before the
signed upload URL is issued:

```sql
IF _object_name = 'external_clients__a' AND _field_name = 'quotation' THEN
  -- resolve _caller_role + _custom_role
  IF _caller_role != 'admin' AND lower(coalesce(_custom_role,'')) NOT LIKE '%crm%' THEN
    RETURN QUERY SELECT NULL::UUID, NULL::TEXT, NULL::TEXT, NULL::TEXT, false,
      'Access denied: CRM Office role required to upload quotation';
    RETURN;
  END IF;
END IF;
```

Scoped **only** to `external_clients__a.quotation`. Every other object/field —
including all Stage 1/2 file fields — is unaffected. Auditor, Tech Reviewer, External
Client, and unassigned users can no longer upload quotation at all (blocked before any
bytes are sent).

> Note: this is the **only** hard upload-block in the system. Every other file field
> (application form, agreement, Stage 1/2 report/NCR/RCA/evidences) keeps the existing
> soft-gate convention — the upload always succeeds; only the status auto-advance is
> role-gated in `finalize_file_upload`.

### Follow-up fix: dead `storage.sign_url()` call (migration 235)

`start_file_upload` has, since its original definition in `016_file_upload_rpc_functions.sql`,
called `SELECT storage.sign_url(...) INTO _signed_url` to populate the `upload_url`
return column. Testing Sprint 0 surfaced that this function doesn't exist in this
Supabase project (`function storage.sign_url(text, text, unknown, unknown) does not
exist`), which aborted the entire RPC — no attachment row created, no upload possible,
for any file field, not just `quotation`.

Checked `FileUploadField.tsx:105-124` and confirmed the frontend **never reads**
`upload_url` — it only uses the `attachment_id`/`bucket`/`storage_path` from the RPC
result, then uploads via the authenticated Supabase Storage client
(`supabase.storage.from(bucket).upload(storage_path, file, { upsert: true })`), the
same pattern used for downloads elsewhere (`FileUploadField.tsx:193-195`,
`ClientSummaryTab.tsx:155`). Migration 235 removes the dead call; `upload_url` is now
always `NULL`, which the frontend already ignores. This was a pre-existing bug carried
forward unmodified into migration 232 — not something introduced by the Stage 1/2
work — but it's fixed here since it blocked verifying Sprint 0 at all.

### Follow-up fix: workflow bar didn't refresh after upload (frontend)

Separately: uploading a file (e.g. `quotation`) correctly advances `status__a` in the
database via `finalize_file_upload`, but `FileUploadField` (`FileUploadField.tsx`) had
no way to tell its parent `RecordDetailView` to re-fetch the record afterward — it only
called its own internal `loadAttachments()`. `ClientWorkflowBar` reads `status__a` from
`RecordDetailView`'s `recordData` state, so the stepper wouldn't visibly move until the
user reopened the record or refreshed the page. This predates Stage 1/2 and affects
every file field, not just `quotation`.

Fixed by adding an `onUploadComplete?: () => void` prop to `FileUploadField`, called
after both successful upload and successful delete, wired at both of its mount points
in `RecordDetailView.tsx` to `() => setRefreshKey(k => k + 1)` — the exact same
refresh mechanism already used by `ReviewActionPanel`/`RenewalActionPanel`'s
`onActionComplete`. No new state or pattern introduced.

## S1 — Stage 1 Audit Lifecycle

### Flow

```
CRM/Auditor uploads report ─► Stage1_Report_Uploaded
CRM/Auditor uploads NCR ─────► Stage1_NCR_Uploaded
Client uploads NCR+RCA ──────► Stage1_NCR_RCA_Uploaded
Auditor accepts RCA ─────────► Stage1_Auditor_Accepted        (now in tech review)
Tech Reviewer submits findings► Stage1_Tech_Findings_Given
Auditor closes audit ────────► Stage1_Closed
Tech Reviewer final accept ──► Stage1_Complete
```

Reject step-backs:
- Auditor rejects RCA → `Stage1_NCR_Uploaded` (client re-uploads RCA), notes in `stage1_rejection_notes__a`
- Tech final reject → `Stage1_Tech_Findings_Given` (auditor re-closes), notes in `stage1_tech_final_rejection_notes__a`

The handoff from `Stage1_Auditor_Accepted` into tech review has **no RPC** — the record
simply sits at that status and the Tech Reviewer picks it up by calling
`submit_stage1_tech_findings`.

### Fields (migration 233)

| Field / Column | Type | Set by |
|---|---|---|
| `stage1_report` → `stage1_report__a` | file | Upload (CRM/Auditor) |
| `stage1_report_uploaded_date__a` | DATE | Auto, on upload |
| `stage1_ncr` → `stage1_ncr__a` | file | Upload (CRM/Auditor) |
| `stage1_ncr_uploaded_date__a` | DATE | Auto, on upload |
| `stage1_ncr_rca` → `stage1_ncr_rca__a` | file | Upload (linked client) |
| `stage1_ncr_rca_uploaded_date__a` | DATE | Auto, on upload |
| `stage1_auditor_accepted_date__a` | DATE | `review_stage1_ncr_rca` accept |
| `stage1_rejection_notes__a` | TEXT | `review_stage1_ncr_rca` reject |
| `stage1_tech_findings_notes__a` | TEXT | `submit_stage1_tech_findings` |
| `stage1_tech_findings_file` → `stage1_tech_findings_file__a` | file (optional) | Upload (Tech Reviewer) |
| `stage1_tech_findings_date__a` | DATE | `submit_stage1_tech_findings` |
| `stage1_closure_notes__a` | TEXT | `close_stage1_audit` |
| `stage1_closed_date__a` | DATE | `close_stage1_audit` |
| `stage1_tech_final_accepted_date__a` | DATE | `accept_stage1_tech_review` accept |

| `accept_stage1_tech_review(p_record_id, p_action, p_notes)` | Tech Reviewer/admin | `Stage1_Complete` + date | `Stage1_Tech_Findings_Given` + notes |

## Design Notes & Constraints

- **`status__a` is plain TEXT** — no ENUM or CHECK constraint. All stage-value strings
  are an app-level convention hardcoded in the RPCs (consistent with the whole app;
  no workflow RPC reads `tenant.picklist_values`). The stage strings are **not** yet
  registered in `tenant.picklist_values`, so they won't appear in the generic
  edit-mode dropdown — optional cosmetic follow-up (Sprint 5), no functional impact.

- **Two dedicated rejection-notes columns per stage** (`stage*_rejection_notes__a` for
  the RCA checkpoint, `stage*_evidences_rejection_notes__a` for evidences,
  `stage*_tech_final_rejection_notes__a` for final sign-off) — because each stage has
  multiple reject checkpoints with different step-back targets; a single shared column
  would make it ambiguous which rejection a note belongs to.

- **No file-existence precondition on accept RPCs** — an Auditor/Tech Reviewer can
  accept even if the corresponding file was never uploaded. This matches the existing
  app convention (`review_client_agreement`, `review_surveillance_intimation` behave
  the same); the "only show the button when the file exists" guard lives in the
  frontend, which for these stages is not built yet.

- **Any user with the role can act on any record** — there is no per-record assigned
  auditor / tech reviewer (confirmed decision). Accountability is via
  `attachments.uploaded_by` and the `updated_by` audit field, resolved to a name at
  read time (see **created-by-updated-by.md**).

- **Date/text columns are not registered in `tenant.fields`** — only the file fields
  are. `tenant.get_object_records` (migration 230) builds `record_data` from
  `information_schema.columns`, so every physical column reaches the frontend
  regardless; the workflow bar will read the dates directly. Register them later only
  if you want them to appear as labeled fields in the record detail form.

- **Manual reference dates** — the 7 dates you plan to add by hand (`Stg 1 date`,
  `Stage 2 date`, `Stage 2 start date`, `Tech review stg1/stg2 Date`, `Client
  agreement date`, `Application date`) mostly overlap columns created here or existing
  ones (e.g. `stage1_tech_final_accepted_date__a`, `stage2_tech_final_accepted_date__a`,
  existing `Client_Agreement_Signed_Date__a`, `Date__a`). Only "Stage 2 start date" is
  genuinely new. See the sprint-plan doc's mapping table before adding, to avoid
  duplicates.

## Verification

Applied via the normal Supabase deploy path (no service-role key locally). Per-sprint
checks:

**S0** — as a non-CRM/non-admin user, attempt a `quotation` upload → expect
`Access denied: CRM Office role required to upload quotation`. As CRM/admin → succeeds.

**S1 / S2** — impersonate a user in the SQL editor (the editor's own session has a null
`auth.uid()`), then exercise one RPC end-to-end:

```sql
BEGIN;
SELECT set_config('request.jwt.claims',
  json_build_object('sub', '<admin_or_auditor_user_id>')::text, true);

SELECT * FROM public.review_stage1_ncr_rca('<record_id>', 'accept', NULL);
SELECT status__a, stage1_auditor_accepted_date__a
FROM tenant.external_clients__a WHERE id = '<record_id>';
COMMIT;
```

Expect `success = true` and `status__a = 'Stage1_Auditor_Accepted'` with today's date.
Repeat the pattern for the Stage 2 RPCs. Role-deny check: run the same as a user whose
custom role lacks `auditor`/`tech` → expect the `Access denied` message. Admin bypasses
every gate, so it works regardless of custom role.
