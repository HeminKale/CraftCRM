## 1. Page layout — `cdc_report` and `stage2_audit_date` placed

Both fields were registered by migration 238 but never placed on any layout section
(confirmed absent via `get_layout_blocks` before this session). Added to the existing
**"stage 2 audit"** section — same section as Stage 2's five file fields — via
Settings → Object Manager → External Clients → Page Layout, same pattern used for
every other field placement in this epic.

**Verified live**, fresh session, server-refetched (not local component state):
`get_layout_blocks` response for `external_clients__a` includes both `cdc_report`
("CDC Report") and `stage2_audit_date` ("Stage 2 Audit Date") in section
`stage 2 audit`, and the "Layout saved successfully!" confirmation fired on save.

**Bug found and worked around (not fixed — flagging for a decision):** the Page
Layout editor's field-pool search box
([`FieldPool.tsx:71`](../../app/commonfiles/core/components/settings/FieldPool.tsx#L71))
crashes the whole page with a Next.js dev-overlay `TypeError: Cannot read properties
of null (reading 'toLowerCase')` whenever a typed query doesn't match a button's
`label`/`name` and falls through to `button.button_type.toLowerCase()` on a button
row whose `button_type` is `NULL`. It doesn't crash on page load or on an empty query
— short-circuit evaluation (`||`) hides it until a non-matching search string is
typed, which is exactly the everyday use case. This is why it wasn't caught during
Sprint 3/4's layout work (fields were clicked directly off the unfiltered pool list,
never searched). Worked around here by skipping the search box entirely and clicking
fields directly in the (short, unvirtualized) pool list. **This is a pre-existing
frontend bug unrelated to the Stage 1/2 schema/RPC work** — not fixed, per this
sprint's "ask before further changes" scope; flagging for the stakeholder to decide
whether it's worth a follow-up fix. It likely affects the Page Layout editor for
*any* object that has a button with a null `button_type`, not just External Clients.

## 2. Reference-dates mapping — corrected in the sprint-plan doc

The mapping table in **UAF-2_external-client-audit-workflow-sprint-plan.md** predated
migration 238's Stage 2 tail restructuring (`close_stage2_audit` and
`accept_stage2_tech_review` retired — see S4.md) and pointed two rows at a column,
`stage2_tech_final_accepted_date__a`, that no live code path writes anymore. Corrected
in place (see the doc for the full table with rationale inline):

| Reference date | Old (stale) mapping | Corrected mapping |
|---|---|---|
| Stage 2 date | `stage2_tech_final_accepted_date__a` | **`stage2_registration_date__a`** — set by `set_stage2_registration_date`, the actual Stage 2 completion signal post-238 |
| Tech review stg2 Date | `stage2_tech_final_accepted_date__a` | **`stage2_tech_findings_date__a`** — set by `submit_stage2_tech_findings` |
| Stage 2 start date | "genuinely new, add as planned" | **`stage2_plan_sent_date__a`** — added by migration 238, no longer needs a new field |

Unaffected and still correct: Stg 1 date / Tech review stg1 Date →
`stage1_tech_final_accepted_date__a`; Client agreement date →
`Client_Agreement_Signed_Date__a`; Application date → `Date__a`.

**Net effect: all 7 originally-planned reference dates are now covered by existing
columns.** None need to be added as new fields — including "Stage 2 start date",
which the original doc flagged as genuinely new before 238 added
`stage2_plan_sent_date__a`.
