# External Client — Stage 1 Audit Workflow: Frontend + Realignment (Sprint 3)

This document covers **Sprint 3** — the Stage 1 frontend, plus a **backend realignment
(migration 237)** that reshapes what Sprint 1 built to match the agreed business flow.
Stage 2 is Sprint 4 and is not touched here.

> **Read this before S0_S1_S2.md's Stage 1 sections.** Migration 237 supersedes parts
> of 233 — where the two disagree, 237 is current. S0_S1_S2.md remains accurate for
> S0 (quotation lock) and S2 (Stage 2), neither of which changed.

**Pending sprints/Sprint_2 pending.md**.

## Why a realignment was needed

The Stage 1 backend merged in migration 233 did not match the business flow. Validating
the agreed spec against the merged code surfaced four structural gaps:

| Gap | 233 as merged | Agreed flow |
|---|---|---|
| No plan round | Stage 1 began at report upload | Plan is uploaded, **client accepts/rejects it**, *then* the audit happens |
| No audit date | — | CRM/Auditor sets a **manual** Stage 1 Audit Date |
| Report + NCR split | Two statuses, two date stamps | **One** status, no date |
| RCA review gate too narrow | Auditor only | **Auditor or CRM Office** |

Two items in the spec were **deliberately not adopted**, confirmed with the stakeholder:

- **The final gate stays with the Tech Reviewer.** The spec's last row ("Auditor/CRM
  accepts → Ready for Stage 2") would have inverted 233's tail. Instead the existing
  chain (`submit_stage1_tech_findings` → `close_stage1_audit` →
  `accept_stage1_tech_review`) is kept as-is, and the terminal status `Stage1_Complete`
  is simply **relabelled** "Ready for Stage 2". No data migration, no RPC rewrite.
- **The client does not formally accept the NCR sheet.** Uploading the NCR + RCA *is*
  the acceptance — there is no status or RPC for a separate NCR acknowledgement.

To honour the spec's "tech reviewer can add findings **or directly accept**" while
keeping 233's tail intact, the findings notes are now **optional**: submitting an empty
box is the direct-accept path. This is a frontend-only change; the RPC already accepted
`NULL` notes.

## Status flow (current)

```
Application_Sent → Application_Accepted → Quotation_Received
  → Client_Agreement_Signed
  → Stage_one_plan_Sent        (CRM/Auditor uploads audit plan — auto)
  → Stage1_Plan_Accepted       (client accepts plan)
  → Stage1_Report_Sent         (CRM/Auditor uploads report and/or NCR — auto)
  → Stage1_NCR_RCA_Uploaded    (client uploads NCR + RCA — auto)
  → Stage1_Auditor_Accepted    (auditor/CRM accepts RCA)
  → Stage1_Tech_Findings_Given (tech reviewer submits findings, or accepts w/o)
  → Stage1_Closed              (auditor closes)
  → Stage1_Complete            (tech reviewer signs off — shown as "Ready for Stage 2")
```

**Reject step-backs:** client rejects plan → stays `Stage_one_plan_Sent` + client
remarks; auditor rejects RCA → `Stage1_Report_Sent` + auditor remarks; tech final
reject → `Stage1_Tech_Findings_Given` + rejection notes.

**Retired values:** `Stage_one_Audit_Done`, `Report_Sent` (dropped from the main
pipeline per the spec), `Stage1_Report_Uploaded`, `Stage1_NCR_Uploaded` (merged).
All four are deactivated in `tenant.picklist_values` rather than deleted, so historical
records still resolve.

## Migration 237 — [`237_stage1_workflow_realignment.sql`](../../supabase/migrations/237_stage1_workflow_realignment.sql)

✅ **Applied and verified** (see "Verification status" below).

| § | What it does |
|---|---|
| 1 | Adds `stage1_plan_accepted_date__a`, `stage1_plan_client_remarks__a`, `stage1_audit_date__a` |
| 2 | Registers `stage1_audit_date` in `tenant.fields` as a **date** field — unlike the other Stage 1 dates it is set by hand, so it must be an editable layout field |
| 3 | Relabels `stage1_report` → "Stage 1 Audit Report", `stage1_ncr_rca` → "Stage 1 NCR + RCA" (**labels only** — api names are string-matched inside `finalize_file_upload`/`start_file_upload` and must never change) |
| 4 | Registers all 12 status values in `tenant.picklist_values` in bar order; deactivates the 4 retired ones |
| 5 | Migrates live records off `Stage1_Report_Uploaded`/`Stage1_NCR_Uploaded` → `Stage1_Report_Sent` |
| 6 | **New RPC** `review_stage1_plan(p_record_id, p_action, p_notes)` — linked-client gated |
| 7 | **Redefines** `review_stage1_ncr_rca` — gate widened to CRM, reject repointed to `Stage1_Report_Sent` |
| 8 | **Redefines** `finalize_file_upload` — adds `stage_one_audit_plan` auto-advance, merges report/NCR |

**`finalize_file_upload` ordering:** 237 is now the live definition, reproducing 234's
body verbatim plus the Stage 1 changes. If these migrations are ever replayed, **237
must run after 234** or Stage 2's auto-advance blocks are lost.

**Audit plan field:** `stage_one_audit_plan` is the upload target (the one actually on
the record layout). The similarly-named legacy `Stage_one_audit Plan` field is *not*
wired to anything and was left untouched.

> Note: `stage_one_audit_plan` is type **`files`** (multiple), not `file`. Uploads
> therefore *append* rather than replace, and each new upload re-fires the auto-advance
> — resetting `status__a` to `Stage_one_plan_Sent` and re-stamping the sent date. That
> is the intended behaviour for a revised plan (it re-opens the client's acceptance
> round), but it does mean uploading a plan after acceptance silently rewinds the
> record to awaiting-acceptance.

## Frontend

### [`ClientWorkflowBar.tsx`](../../app/commonfiles/core/components/custom/External_Client/ClientWorkflowBar.tsx) — one bar, sliding window

Rebuilt as a **single** unified bar (an earlier draft had two separate steppers; that
was rejected). One `STAGES` array = one dot per `status__a` picklist value, in the same
order as §4 of the migration — the two must be kept in sync, and **Stage 2's values
append to this same array in Sprint 4**.

With 12 stages (≈21 after Stage 2) the full track doesn't fit, so it renders a
**7-wide window** centred on the current stage — `current-3 … current … current+3` —
clamped so it never runs off either end. A `+N more` chevron on the right expands to
the full pipeline in a horizontally-scrollable track.

`StageTrack` takes the slice plus a global `offset`, so connector colouring and
completion state stay correct on a clipped window, and clipped edges render
continuation stubs rather than gaps. `dateKey: ''` marks a stage with no date
(`Stage1_Report_Sent`), which renders a dot with no caption.

### [`StageAuditActionPanel.tsx`](../../app/commonfiles/core/components/custom/External_Client/StageAuditActionPanel.tsx) — checkpoints

| Panel | Shown to | Gate | RPC |
|---|---|---|---|
| Upload / **Revise** Audit Plan | CRM / Auditor | plan not uploaded, **or** rejected by client | — (generic field) |
| Review Audit Plan | Linked client | `Stage_one_plan_Sent` + plan uploaded | `review_stage1_plan` |
| Conduct Stage 1 Audit | CRM / Auditor | `Stage1_Plan_Accepted` | — (set date + upload via fields) |
| Upload NCR + RCA | Linked client | `Stage1_Report_Sent` | — (generic field) |
| Review NCR + RCA | **Auditor or CRM** | `Stage1_NCR_RCA_Uploaded` | `review_stage1_ncr_rca` |
| Tech Review | Tech Reviewer | `Stage1_Auditor_Accepted` | `submit_stage1_tech_findings` (notes optional) |
| Close Stage 1 Audit | Auditor | `Stage1_Tech_Findings_Given` | `close_stage1_audit` |
| Final Sign-Off | Tech Reviewer | `Stage1_Closed` | `accept_stage1_tech_review` |

Role resolution is unchanged from the existing convention: admin bypasses everything;
`crm`/`auditor`/`tech` match as case-insensitive substrings of the custom role name;
linked client is `client_user_id__a === currentUserId`.

**Remarks surfacing** — `stage1_plan_client_remarks__a` (client's plan rejection) shows
to CRM/Auditor on the revise prompt; `stage1_rejection_notes__a` (auditor remarks) shows
to the client on the RCA upload prompt; `stage1_tech_final_rejection_notes__a` shows to
the auditor on the closure panel. Admin gets a read-only fallback box for all three when
no checkpoint is active. Remarks columns are deliberately **not** registered in
`tenant.fields` — they're written by RPCs and surfaced read-only by the panel, matching
the existing `rejection_notes__a` convention.

**Uploads never happen inside the panel** — all file fields go through the generic
[`FileUploadField`](../../app/commonfiles/core/components/Application/FileUploadField.tsx)
on the layout, same separation of concerns as `RenewalActionPanel`. `FileUploadField`
was not modified in this sprint.

### [`RecordDetailView.tsx`](../../app/commonfiles/core/components/Application/RecordDetailView.tsx)

`StageAuditActionPanel` mounts immediately after `ReviewActionPanel` inside the existing
External-Client gate (~line 1671), with the same identity props and the same
`onActionComplete={() => setRefreshKey(k => k + 1)}` — no new refresh mechanism.

## Page layout

A **"stage 1 audit"** section was added to the External Client page layout (Settings →
Object Manager → External Clients → Page Layout) containing the 4 Stage 1 file fields,
which existed in `tenant.fields` but were on no layout — so nobody could upload through
them. This is a `tenant.layout_blocks` **data change**, already applied and verified.

The **Stage 1 Audit Date** field (registered by 237 §2) has since been added to the
layout as well, so CRM/Auditor can set it at the `Stage1_Plan_Accepted` step.

To redo on another tenant: Page Layout → **Add Section** → name it, type "Fields Only"
→ click each field in the pool → pick the section → **Save Layout**.
